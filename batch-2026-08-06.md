## The one thing that needs you

**FCC-26 — and it needs a word, not a review.**

It was already stalled once, on 2026-08-02, for the same reason. The FreeCAD API
takes a string for `AttachmentSupport`, not a face object, so "keep the reference
computed" cannot mean "write no name", and what it does mean is a product
decision. Worse, `tests/test_lint.py::test_a_computed_reference_is_accepted`
asserts that `'Edge%d' % index` **is** a computed reference — so the rule this
ticket asks for would delete a test that states today's opposite rule.

What I added this round was a measurement that narrows it. I built the
reproduction and changed the parameter upstream:

```
before: 6 faces, top = Face6, attached at z=10
pad.Length 10 → 25 → attached at z=25, state ['Up-to-date']
```

The frozen name **survived**. A parameter change that does not reorder the
topology leaves `Face6` meaning the same face — so the third acceptance
criterion already passes for the common case, and the rule being asked for
would refuse a construction that is usually correct.

The three ways out, with a recommendation, are in the ticket. Reply with a
number and it is an hour's work.

## What FreeCAD 1.1 changed under us

Worth reading even if you skip the rest.

**FCC-27's central symptom no longer exists.** `Result has multiple solids.
Only keeping the first.` was a FreeCAD **1.0** behaviour. On 1.1.3:

```
             pad.solids  body.solids   volume
disjoint          2           2        1570.8    (1.0: 1 solid, 785.4 — exactly half)
overlapping       1           1        1347.1
single            1           1         785.4
```

Nothing is discarded. Both mechanisms the ticket named are moot — there was
never a console message to read headless, and there is no longer a loss to
count. But upstream's fix left a *cleaner* signal for the same modelling
mistake: the Body is simply in two pieces, and `len(shape.Solids)` says so. That
is what Preflight now refuses.

The general lesson: **the 2026-07-31 session log is a 1.0 artifact.** Anything
else derived from it deserves a re-measurement on 1.1 before it is built. That
applies to the remaining children of FCC-24.

## Findings worth keeping

Things that were not in any ticket and turned up while working.

- **FCC-50 quietly armed the FCC-44 bug.** Adding the Base-URL write to
  `saveSettings` connected `base_urls_changed` to the same handler that
  destroyed the model combos mid-save. A user who only ever edited a Base URL
  would have hit it. Both are ordered behind the read now — but the two tickets
  were four hours apart in the same batch, and only doing them in sequence
  caught it.
- **A Body's Origin was setting the render's framing.** Three axes and three
  datum planes, each 1e100 across. Under the old renderer their planes
  tessellated to nothing so they were invisible; under the new one their *edges*
  are real geometry, and per-pixel sampling of a 1e100-long segment asks numpy
  for an array it refuses to allocate. It took the Preflight Worker down and
  broke the vertical slice outright. The render now draws what has surfaces and
  finite bounds — which is what the viewport draws.
- **That is also why the suite got six times faster.** 145 s → 26 s. The old
  renderer was drawing polygons for infinite datum planes on every Preflight.
- **Review agreed with the measurement, and that is not the same as Review being
  right.** On FCC-30 it passed the bracket on the render, and the bracket was
  exact to 2e-6 %. But Review never sees a number. The same render would have
  come back `pass` for a bracket with the fillet on the wrong edge or a hole 5 mm
  off — nothing in the picture distinguishes them at that angle. The agreement is
  real evidence that the *model* built the part; it is no evidence that Review can
  judge mass. That is the gap FCC-46 is standing next to.
- **The pip layering was provable in two commands.** `pip install --target`
  without `--upgrade` refuses to overwrite the existing file and writes the new
  dist-info anyway — so the metadata says 1.16.0 while the code is still
  1.15.0. That is not "two versions side by side" as a tidiness problem; it is
  new metadata over old code, which is exactly how a pydantic stops matching its
  pydantic_core.

## What is not verified

Said plainly, because a lot of this batch's acceptance criteria are
*live provider* and this batch could not run one.

- **FCC-25** — five of its six criteria are live-provider. The machinery is
  built and tested; whether the model actually asks for "модельку шестерні"
  is unmeasured. The prompt is where that behaviour lives —
  `config/prompts/plan.md`, the paragraph beginning "Ask before you plan".
- ~~**FCC-38**~~ — **now verified.** The route the trap names works end to end
  through Preflight into a Document, and FCC-30's live run showed the model
  *takes* it on the first attempt: `materials("aluminium")` returned 0 results,
  the model retried `materials("aluminum")`, got 7, and picked
  `Aluminum-Generic` for its 2700 kg/m³ density. Step 6 is where the 2026-08-02
  run died; this one walked through it.
- **FCC-46** — one acceptance criterion is **not met**: a reference screenshot
  from the live GUI viewport, committed as a fixture. That needs a running
  FreeCAD with a GL context, which is a Level 3 artifact by this project's own
  lanes. I did not substitute anything for it. Three renders are attached to the
  ticket instead — they read as viewport pictures, but that is an eye, not a
  threshold.
- **FCC-48** — this machine is PySide6, where `QPixmap(QImage)` happens to work,
  so only the null-conversion half is red here. The Qt5 half of the claim comes
  from Qt5's API, not from measurement.
- **FCC-28** — the pydantic serializer warning itself was only ever seen against
  a paid call in the report view. What is proven is that the installer can no
  longer create the mismatch, and repairs it if it finds one.
